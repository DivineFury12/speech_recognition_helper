# GigaAM-v3 ASR backend

## Запуск

GPU (Docker Desktop с поддержкой NVIDIA GPU или NVIDIA Container Toolkit на Linux):

    docker compose up --build

CPU:

    docker compose -f docker-compose.cpu.yml up --build

При первом старте скачиваются веса голосовой модели. Веса текстовой модели
эмбеддингов скачиваются при первой записи или поиске; этот запрос может
выполняться дольше обычного.
Для GPU Docker Compose требует доступную CUDA и завершит запуск с ошибкой, если
модель не удалось разместить на видеокарте. Веса сохраняются в томе `model-cache`.

## Проверка

    curl http://localhost:8000/health
    curl -F "file=@example.wav" http://localhost:8000/transcribe

Swagger: http://localhost:8000/docs
В ответе `/health` поле `device` должно быть `cuda:0` при запуске GPU-варианта.

## API-контракт для фронтенда

Полная схема прототипа находится в [openapi.yaml](../openapi.yaml). В ней описаны
текстовые и голосовые запросы ассистенту, уточнения в рамках диалога, задачи,
напоминания, встречи, поиск и озвучивание ответа.

Статус каждой операции указан в `x-implementation-status`. Сейчас работают
`/health`, `/transcribe` и `/transcribe_longform`. Маршруты
`/v1/assistant/messages` и `/v1/assistant/audio` принимают запросы. Без
`GIGACHAT_AUTH_KEY` они возвращают `501`; с ключом отправляют текст в GigaChat,
проверяют структурированную команду и через PostgreSQL выполняют создание,
список и поиск записей. Успешное действие возвращает `status: completed`.
`GET /v1/entries` и `GET /v1/entries/search` также работают с БД.
Остальные ручки описаны только в контракте. `/docs` и `/openapi.json` показывают
зарегистрированные FastAPI-маршруты.

Приоритет указан отдельно в `x-requirement-level`:

| Уровень | Ручки | Для чего |
| --- | --- | --- |
| `core` | `POST /v1/assistant/messages`, `POST /v1/assistant/audio` | Четыре обязательных действия по естественному запросу; текстовый и голосовой ввод. |
| `supporting` | `GET /v1/entries`, `GET /v1/entries/search` | Прямой доступ фронтенда к списку и поиску. Логика обязательна, но отдельные URL в задании не требуются. |
| `supporting` | `GET /health`, `POST /transcribe` | Проверка сервиса и распознавание речи для голосового сценария. |
| `additional` | Длинное аудио, история диалога, прямое создание/получение/изменение/удаление записи, TTS | Возможности сверх минимального результата задания; точные пути помечены в схеме. |

В PDF требуются **четыре действия**, а не определённые URL: создать задачу или
напоминание, создать встречу, показать записи за период и найти старую запись.
Голосовой и текстовый ввод тоже входят в минимальный сценарий. Статус выполнения
записи необязателен; озвучивание ответа и семантическое ранжирование поиска можно
добавить после работающего MVP.

### Как подключать кнопки на фронтенде

- **Голосовая кнопка:** записать короткое аудио и отправить один
  `multipart/form-data` запрос на `POST /v1/assistant/audio` с полями `file` и
  `timezone`. Сервер распознаёт речь и передаёт текст в общую логику ассистента.
- **Текстовая кнопка:** отправить `POST /v1/assistant/messages` с JSON-полями
  `text` и `timezone`. Сервер вызывает ту же логику ассистента.
- Оба маршрута возвращают `AssistantTurn`: `user_text` (в голосовом сценарии —
  распознанная речь), `assistant_text`, `status` и `entries`. Фронтенд показывает
  ответ и при необходимости созданные или найденные записи.
- `POST /transcribe` остаётся вспомогательной ручкой: она возвращает только
  `{ "text": "..." }`, не создаёт запись и не выполняет команду. Её можно
  использовать для проверки ASR или предварительного редактирования текста.

Оба маршрута ассистента передают текст в один сервис обработки команд.
`status: no_action` означает, что действие не было выполнено, например из-за
нехватки даты или названия.

### Подключение GigaChat API

Скопируйте `.env.example` в `backend/.env` и укажите `GIGACHAT_AUTH_KEY` —
**ключ авторизации** из кабинета GigaChat API. Сервер сам получает и обновляет
токен доступа. `GIGACHAT_SCOPE` по умолчанию `GIGACHAT_API_PERS`, а
`GIGACHAT_MODEL` — `GigaChat-2`; укажите доступные вашему проекту значения.
После настройки пересоздайте контейнер командой `docker compose up -d --build`.
Ключ хранится только на backend и не передаётся фронтенду.

### PostgreSQL и векторный поиск

Compose запускает PostgreSQL с расширением `pgvector` во внутренней сети и
сохраняет данные в томе `postgres-data`. При старте бэкенда Alembic применяет
миграции. Параметры `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` можно
задать в `backend/.env`; при внешней БД задайте `DATABASE_URL` в формате
`postgresql+psycopg://user:password@host:5432/database` и убедитесь, что в ней
доступно расширение `vector`.

При создании записи сервер получает вектор названия локально на CPU. Модель
задаётся через `EMBEDDING_MODEL`: `e5` (по умолчанию,
`intfloat/multilingual-e5-small`, 384 координаты) или `frida`
(`ai-forever/FRIDA`, 1536 координат). Полные имена моделей также принимаются.
Векторы хранятся в `entry_embeddings` отдельно для каждой модели, поэтому
переключение не уничтожает уже созданные векторы. FRIDA значительно тяжелее;
при первом использовании её веса скачиваются в `model-cache`.

Для переключения задайте `EMBEDDING_MODEL=frida` в `backend/.env` и
пересоздайте контейнер бэкенда: `docker compose up -d --build gigaam`.

Поиск сначала проверяет вхождение текста, затем добавляет близкие по
косинусному расстоянию записи. Он использует векторы выбранной модели. Чтобы
старые записи тоже участвовали в смысловом поиске после переключения, выполните:

    docker compose exec -T gigaam python -m src.reindex_embeddings

Команда создаёт только недостающие векторы выбранной модели. Для пробного
запуска можно добавить `--limit 10`. Если модель недоступна, создание записи
сохраняет её без вектора, а поиск продолжает работать по тексту.

Записи и диалоги сейчас общие для всех посетителей. Перед публичным размещением нужно
добавить разделение пользователей или демо-сессий.

Docker-образ включает корневой сертификат Минцифры, необходимый GigaChat API,
и по умолчанию использует системный CA bundle. Для другого окружения можно задать
`GIGACHAT_CA_BUNDLE` как путь к доверенному CA bundle **внутри контейнера**.
Ошибки авторизации, сети и неверного ответа модели возвращаются как `502`.
Порядок получения токена и формат структурированного вывода описаны в
[документации GigaChat по авторизации](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api)
и [по JSON-схемам](https://developers.sber.ru/docs/ru/gigachat/guides/structured-output).

### Контракт внешней модели

Модель должна вернуть один JSON-объект `AssistantCommand`, а не свободный текст.
Схема проверяется в `src/schemas/assistant_command.py` и также описана в
`openapi.yaml`. Например:

```json
{
  "action": "create_entry",
  "kind": "reminder",
  "title": "Позвонить Ивану",
  "date": "2026-10-12",
  "date_phrase": "завтра",
  "time": "10:00",
  "time_phrase": "в 10:00",
  "date_from": null,
  "date_to": null,
  "query": null
}
```

Для списка модель возвращает `action: list_entries` и даты `date_from` /
`date_to`; для поиска — `action: search_entries` и `query`. Все поля ответа
присутствуют; для отсутствующих данных модель возвращает `null`. Относительные даты вычисляются по
`today` и часовому поясу запроса. Некорректное действие, время, период или
посторонние поля отклоняются до выполнения команды.

`src/services/assistant.py` формирует `AssistantTurn` из проверенной команды и
выполняет действие через сервис записей. Ответы GigaChat с неверной структурой
отклоняются.

При нехватке данных ассистент задаёт уточняющий вопрос и сохраняет
незавершённую команду в PostgreSQL. Фронтенд передаёт полученный
`conversation_id` в следующих запросах; история доступна через
`GET /v1/conversations/{conversation_id}/messages`. Для новой беседы ID
опускается. Даты и время создаваемых записей проверяются по фразам из
сообщения; неподтверждённые значения не сохраняются. Время передаётся
вместе с часовым поясом IANA, например `Europe/Moscow`.

- GET  /health

                                (HF_TOKEN=xxx docker compose up --build)

v3_rnnt, v3_ctc.
